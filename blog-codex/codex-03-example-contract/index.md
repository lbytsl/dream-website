## 技巧：用输入输出样例消除歧义

**先让 Codex 用一张输入输出表复述业务规则，确认有分歧的那一行，再开始写函数。**

## 原理与适用场景

样例表适合「至少」「超过」「每满」这样的边界词。本例上游已经算好字数，传入非负整数；本次只把字数换成阅读分钟，不讨论中文分词。编辑约定每分钟 300 字，空稿显示 0，非空稿不足一分钟也计一分钟。

## 低效写法与问题

```js
const minutes = Math.round(words / 300);
```

只拿 300 字试一次会得到正确的 1，看不出问题。换成 1 字会显示 0，换成 301 字又少算了一分钟。「大概估一下」无法区分这两个规则。

## 正确做法与代码解释

> 先不要实现。请用 0、1、299、300、301 五个字数列出结果，解释哪一行能区分四舍五入和向上取整。我确认后，再把表写成检查。

| 字数 | 0 | 1 | 299 | 300 | 301 |
| --- | --- | --- | --- | --- | --- |
| 期望分钟 | 0 | 1 | 1 | 1 | 2 |

确认后，下面的 `reading-time.mjs` 可以直接用 `node reading-time.mjs` 检查：

```js
import assert from 'node:assert/strict';
const readingMinutes = words => Math.ceil(words / 300);
for (const [words, expected] of [[0, 0], [1, 1], [299, 1], [300, 1], [301, 2]]) {
  assert.equal(readingMinutes(words), expected, `${words} 字`);
}
```

`Math.ceil` 只在商有小数时进一；300 不会多出一分钟，0 也不需要特殊分支。最有价值的不是五个样本的数量，而是 300 的两侧都有人把守。

## 关键点与常见陷阱

- 期望列由业务决定，不要让 Codex 用待测函数现算「正确答案」。
- 不要偷偷扩大输入范围。负数、空值是否拒绝，是单独的契约，不是取整方式能回答的问题。

## 动手练习与小挑战

**练习：** 把函数换回 `Math.round`，找出表里哪两项失败。先看报错中的字数，再解释计算过程。

**小挑战：** 编辑决定改成每分钟 400 字。先自己写出 399、400、401 的期望分钟，再让 Codex 改实现；旧的字数样例哪些也需要更新？
