编辑后台把作者字段从 `author` 改成了 `authorName`。新稿能显示，半年前的文章却只剩「匿名」；一次全局替换没法替旧数据改名。

## 技巧：用适配函数保住接口契约

**请 Codex 先列出数据的生产方、消费方和仍然存在的旧格式，再在一个入口统一转换。**

## 原理与适用场景

接口契约是双方约定的数据形状。小书架有旧 JSON 文件和新的编辑器，它们都喂给文章卡片与 RSS。如果四个地方各自猜作者字段，迟早会出现网页有署名、订阅源却没有的情况。最便宜的兼容点通常在读入数据的那一层。

## 低效写法与问题

> 在全仓库把 `author` 替换成 `authorName`，再把测试改成匹配新字段。

这种做法同时改了生产者、消费者和证据，已经保存的旧 JSON 一字未动。测试只使用新数据时仍然能通过。

## 正确做法与代码解释

> 先找出谁写作者字段，谁读它，以及一份真实结构的旧样本（用假名）。新增一个转换函数，供卡片和 RSS 共用；两个字段同时出现时新字段优先，二者都缺才用「匿名」。不要批量改存量文件。

```js
import assert from 'node:assert/strict';
function byline(post) {
  return post.authorName ?? post.author ?? '匿名';
}
assert.equal(byline({ author: '小林' }), '小林');
assert.equal(byline({ authorName: '阿乐', author: '旧名' }), '阿乐');
assert.equal(byline({}), '匿名');
```

运行这段 `.mjs` 后，再让 Codex 在两个展示入口用 `byline(post)` 替代直接读取字段。左到右的 `??` 确定了新旧优先级；只加函数、不改调用方，线上效果仍然不会变。检查时让它逐一指出两个入口的调用位置。

## 关键点与常见陷阱

- 本例把 `null` 和缺失视为无值，空字符串仍保留。若空白署名也不合法，应先问清规则再加样例。
- 「最近创建的两篇都正常」不等于历史兼容。测试要保留旧形状，不能随生产代码一起全部改新。

## 动手练习与小挑战

**练习：** 给旧文章与同时含新旧字段的文章各生成一张卡片和一条 RSS。对照两处读者看到的名字，而不只看转换函数通过。

**小挑战：** 现在产品要求全空格的新署名回退到旧名。先造一个能失败的样本；能否只改转换函数，不再碰两个展示入口？
