# 技巧 10：把项目规范写进 CODEBUDDY.md

> 一句话概括：把每次都要重复说的项目约定写进记忆文件，让它随每次会话自动加载。

{/* truncate */}

本篇聚焦 CodeBuddy 的记忆文件和规则分层。跨工具的方法和练习见[通用技巧](/blog/general-tips/04-repository-instructions)。

## 一、技巧名称与一句话概括

**技巧名称**：项目级持久记忆（Persistent Project Memory）。

**一句话概括**：在 `CODEBUDDY.md` 里写清项目约定、常用命令和禁区，AI 每次启动都会自动读到，你不必反复交代。

这是[通用 02 · 从入口收集上下文](/blog/general-tips/02-focused-context)的「一次投入、长期省空间」解法。

## 二、核心原理与适用场景

CodeBuddy Code 提供四种分层记忆位置，按作用范围划分：

| 类型 | 位置 | 用途 | 共享范围 |
|------|------|------|---------|
| 用户记忆 | `~/.codebuddy/CODEBUDDY.md` | 个人偏好，适用于所有项目 | 仅本人 |
| 用户规则 | `~/.codebuddy/rules/*.md` | 模块化的个人规则 | 仅本人 |
| 项目记忆 | `./CODEBUDDY.md` 或 `./.codebuddy/CODEBUDDY.md` | 团队共享的项目约定 | 随代码仓库共享 |
| 项目规则 | `./.codebuddy/rules/*.md` | 按主题划分的项目指令 | 随代码仓库共享 |
| 项目记忆（本地） | `./CODEBUDDY.local.md` | 个人在此项目的私有偏好 | 仅本人，自动加入 `.gitignore` |

**加载顺序**：用户级主文件与规则 → 项目级主文件（从当前目录向上递归）→ 项目级规则（仅当前目录）→ 子目录记忆（操作子目录文件时动态加载）→ 本地记忆。

用 `/memory` 命令可以查看当前会话实际加载了哪些记忆文件。

**适用场景**：技术栈和编码约定稳定、团队成员共用一套规范、你厌倦了每次新会话都重复说「我们用 TS 严格模式」。

## 三、错误或低效写法及问题说明

**错误一：什么都往里写**

一个 500 行的 `CODEBUDDY.md`，包含完整 API 文档、数据库表结构、三年前的历史决策。结果每次会话一启动，上下文就被吃掉一大块，而且 AI 很难分辨哪些是当前有效的约定。

**错误二：写成口号**

```markdown
# 项目规范
代码要简洁、优雅、可维护。
测试要充分。
性能要好。
```

这些句子和没写一样——没有一条能指导具体决策。

**错误三：把私密信息写进团队共享文件**

把本地数据库密码、测试环境 token 写进 `CODEBUDDY.md`，然后提交到仓库。

## 四、正确应用方式：一份能用的项目记忆

```markdown
# 项目约定

## 技术栈
- React 19 + TypeScript strict + Element Plus
- 包管理：pnpm（不要用 npm install）
- 测试：Vitest，命令 `pnpm test`

## 编码规则
- 组件用 PascalCase，hooks 以 use 开头
- 禁止 `any`，确需使用时加 `// TODO: type this` 注释
- 错误提示统一使用 @src/components/FieldError.tsx
- 每次改动后运行 `pnpm typecheck`

## 目录职责
- src/api/：只放请求封装，不放业务逻辑
- src/utils/：纯函数，禁止引入 React
- backend/：由另一个团队维护，不要修改

## 上下文压缩时保留
- 已修改文件的完整列表
- 所有测试命令与结果
```

**这段内容为什么有效**：

- 每条都是**可验证的规则**，AI 能照着做，你也能检查它有没有照做；
- 「不要修改 backend/」划出红线，避免在跨模块任务里越界（呼应[技巧 01 四要素](/blog/workbuddy-tips/01-task-brief)的约束）；
- 「上下文压缩时保留」是官方最佳实践里推荐的配置，让 `/compact` 不丢关键信息；
- 私有的测试数据、本地路径放 `CODEBUDDY.local.md`，不会进仓库。

配合 `@` 导入还能拆分大文件：

```markdown
# 个人偏好
- @~/.codebuddy/my-project-instructions.md
```

导入可以递归，最深 5 层。注意代码块里的 `@` 不会被当作导入解析。

**再配合规则目录**：把「测试规范」「API 风格」这类主题分别放进 `.codebuddy/rules/testing.md`、`.codebuddy/rules/api.md`，用的时候按需加载，比一个巨型文件更灵活。

## 五、关键点与常见陷阱

**关键点**

1. **控制篇幅**：主文件建议不超过 100 行，细节拆到 `rules/` 目录。
2. **写规则不写历史**：「为什么这么做」放文档，这里只放「现在怎么做」。
3. **团队共享与私人偏好分开**：共享文件进 Git，私人偏好进 `.local.md`。
4. **改了约定就改文件**：过期的 `CODEBUDDY.md` 比没有更危险——AI 会认真执行错误规则。
5. 用 `/memory` 定期检查实际加载了哪些文件，避免以为加载了其实没有。

**常见陷阱**

- **以为写进去就会永远遵守**：长会话里仍可能被早期对话覆盖，重要约束在关键提示词里再强调一次。
- **父目录规则污染**：项目级主文件会向上递归加载直到文件系统根；在深层目录工作时注意上层是否还有别的项目文件。
- **把 `@` 导入写在代码样例里**：代码块中的导入符号不会被解析，别误以为生效了。
- **只写技术栈不写命令**：「用 Vitest」不如「运行 `pnpm test`」可执行。

## 六、动手练习与小挑战

**练习**：为你当前项目写一份 30 行以内的 `CODEBUDDY.md`，至少包含：技术栈、两条编码规则、一条禁区、一条常用命令。写完后开新会话，只说一句「按项目约定给订单模块加个测试用例」，看 AI 是否自动用了你指定的测试命令。

**小挑战**：把你的个人偏好（如「回复用中文」「不要主动提交 Git」）写进 `~/.codebuddy/CODEBUDDY.md`，然后观察跨项目的会话是否都生效了。
