# 技巧 07：让子代理去翻代码——把上下文留给实现

> 一句话概括：探索交给子代理，结论回到主对话——主上下文只留决策所需的信息。

{/* truncate */}

## 一、技巧名称与一句话概括

**技巧名称**：子代理调研（Subagent Delegation）。

**一句话概括**：把「读二十个文件找出答案」这类脏活交给独立上下文的子代理，主对话只收到一份摘要，腾出空间写代码。

官方最佳实践把这条列为最强大的技巧之一，理由很直接：**上下文是根本约束**，而调研过程会吃掉大量上下文。

## 二、核心原理与适用场景

子代理拥有独立的上下文窗口。它启动后自己读文件、自己搜索，结束后只把结论返回给主对话。

对比一下：

| 方式 | 主上下文发生什么 |
|------|-----------------|
| 主对话直接调研 | 20 个文件的全部内容 + 中间推理都堆进主上下文 |
| 交给子代理 | 只增加一段调研结论 |

CodeBuddy Code 里可以用 `/agents` 查看已有子代理，也可以创建新的。常见的内置类型包括：

- `general-purpose`：通用，默认
- `Explore`：只读工具，适合代码库探索
- `Plan`：规划和分析
- 以及 `.codebuddy/agents/` 下的自定义 agent

**适用场景**：代码库调研、跨模块调用链追踪、独立审查、任何「需要读很多文件但只需要一个结论」的任务。

## 三、错误或低效写法及问题说明

```text
请阅读 @src/auth、@src/api、@src/middleware 下所有文件，
搞清楚我们的 token 刷新机制，然后帮我加一个自动续期功能。
```

问题：

1. 三大目录几十个文件全部进入主上下文，剩下能用来写代码的空间大幅缩水；
2. 调研过程中的中间结论、走弯路的记录也留在对话里，干扰后续判断；
3. 到了写实现的时候，AI 可能已经开始「忘」前面读到的细节。

另一种低效做法是让主会话先调研、再开新会话实现——但新会话没有调研结论，又得重来一遍。

## 四、正确应用方式：调研 token 刷新机制

**第一步：派子代理调研**

```text
Use a subagent to investigate how our authentication system handles token refresh:
1. 找出 token 是在哪里签发、存储、刷新的
2. 检查项目里是否已有可复用的 OAuth 或 refresh 工具函数
3. 只返回结论：列出关键文件与行号，不超过 10 条
不要修改任何代码。
```

子代理在自己的上下文里读文件、搜索，主对话只收到 10 条结论。

**第二步：基于结论实现**

```text
根据调研结论，在 @src/auth/token.ts 中增加自动续期逻辑：
- 复用调研中提到的 refresh 工具，不要重复实现
- 请求返回 401 时触发一次刷新，刷新失败则跳转登录
- 验收：npm test -- auth 通过
```

此时主上下文里只有「结论 + 你的需求」，空间充裕。

**第三步：再派一个子代理做验证**

```text
Use a subagent to review this implementation for edge cases:
检查 @src/auth/token.ts 中的并发请求刷新、刷新失败重试、
以及 token 同时过期时的竞态条件。
只报告问题，给出行号，不要修改代码。
```

这正是官方推荐的模式：**用子代理调研、也用子代理验证**，主对话始终专注于实现决策。

**进阶：把子代理固化成 Skill**

如果这类调研经常做，可以用 `context: fork` 把它写进 Skill（见[技巧 12](/blog/workbuddy-tips/17-skill-fork)），一行指令就能启动一个隔离上下文里的专职代理。

## 五、关键点与常见陷阱

**关键点**

1. 给子代理的任务要**有明确产出**：「返回不超过 10 条结论」比「去看看代码」好得多。
2. 明确要求「只读不写」，避免它和主会话同时改文件。
3. 子代理返回结论后，让它附带**文件路径和行号**，方便主会话精准引用（呼应[技巧 02](/blog/workbuddy-tips/02-at-reference)）。
4. 项目级子代理放 `.codebuddy/agents/`，可以随团队共享。

**常见陷阱**

- **子代理也写一大段过程**：提示词里限定输出格式和长度。
- **给子代理的任务太笼统**：「研究一下这个项目」会让它漫无目的地读，结论也没用。
- **多个子代理改同一文件**：并行调研可以，并行写码要配合工作区隔离（见[通用 06 · Git 工作树隔离](/blog/general-tips/06-isolated-worktrees)）。
- **以为子代理记得主对话**：默认情况下 fork 类 Skill 不访问对话历史，重要背景要写进任务本身。

## 六、动手练习与小挑战

**练习**：选一个你熟悉的项目，让主会话直接调研「某个功能涉及哪些文件」，记录它读了多少文件。然后开新会话，用子代理做同样的事，对比主对话里增加的内容量。

**小挑战**：创建一个项目级子代理 `.codebuddy/agents/api-explorer.md`，专门负责「梳理 API 路由与数据模型」，要求返回不超过 15 行的摘要。以后每次要理解 API 层就调用它。
