# 技巧 01：任务描述四要素——让 AI 一次听懂你的需求

> 一句话概括：把任务写成「目标 + 输入 + 输出 + 约束」四段式，AI 就不用靠猜来补全你没说的信息。

{/* truncate */}

## 一、技巧名称与一句话概括

**技巧名称**：任务描述四要素（Goal–Input–Output–Constraints，简称 GIOC）。

**一句话概括**：写提示词时先交代清楚「要什么、拿什么做、交付什么、有哪些不能碰」，让 AI 从「猜意图」切换到「照规格执行」。

这是整个系列的地基。后面所有技巧——引用文件、验收标准、任务拆解、Skills——本质上都是在把这四个要素做得更扎实。

## 二、核心原理与适用场景

WorkBuddy 和 CodeBuddy Code 都是**执行式 Agent**：它们读完你的第一句话，就会据此规划步骤、调用工具、修改文件。第一句话的信息密度，决定了后续每一步的方向。

官方「创建任务」文档建议优先补充四类信息：目标是什么、输入是什么、输出格式、约束条件。这正好对应四要素：

| 要素 | 回答的问题 | 在提示词里的作用 |
|------|-----------|-----------------|
| 目标（Goal） | 要解决什么 | 确定任务边界，防止 AI 顺手做多余的事 |
| 输入（Input） | 依据什么做 | 告诉 AI 去哪读文件、看哪份数据 |
| 输出（Output） | 交付什么 | 定义产物形态，让结果可验收 |
| 约束（Constraints） | 哪些不能碰 | 划出红线，避免破坏既有代码 |

**适用场景**：新建任何开发任务——加功能、修 Bug、做重构、生成测试、写文档。尤其是第一次派活给 AI 时，这四要素能省掉后面五轮来回纠正。

## 三、错误或低效写法及问题说明

看一句非常典型的派活方式：

```text
帮我给登录页加个记住我功能。
```

这句话人能听懂，AI 却只能猜。逐项拆解问题：

- **目标含糊**：加到哪个文件？前端表单还是后端会话？「记住我」是 7 天免登录，还是永久记住账号？
- **输入缺失**：现有登录页在哪？用的 React 还是 Vue？项目有没有现成的 token 存储工具？
- **输出不明**：交付代码就行？还是要补测试、改文档？
- **约束空白**：能不能改后端接口？能不能引入新依赖？要不要保持旧行为兼容？

结果通常有两种：AI 先反问你三四轮；或者它按自己的假设改了一堆文件，你再花更多时间逐个纠正。**省下来的三行字，最后要花三十句对话补回来。**

## 四、正确应用方式：一个真实的登录页任务

假设项目是 React 19 + TypeScript + Element Plus，要给登录页加「7 天内免登录」。四要素写法如下：

```text
目标：为现有登录页增加「7 天内免登录」的记住我功能。

输入：
- src/pages/Login.tsx（登录表单组件）
- src/api/auth.ts（登录请求封装）
- 项目已有 localStorage 工具：src/utils/storage.ts

输出：
- 修改后的 Login.tsx 与 auth.ts
- 新增 src/api/auth.test.ts，覆盖「勾选记住我」和「不勾选」两条分支
- 用文字列出改动文件和改动原因

约束：
1. 不改动后端接口签名，token 仍从登录响应中获取
2. localStorage 只存布尔开关和过期时间，不存明文密码
3. 保持现有表单校验逻辑不变
4. 先给出修改计划，等我确认后再写文件
```

**为什么这样写有效**：

- 目标里有具体时限「7 天」，AI 知道该设多长的过期逻辑；
- 输入给到具体文件路径，配合 `@` 引用（见[技巧 02](/blog/workbuddy-tips/02-at-reference)）可以直接把内容喂进去；
- 输出具体到文件和测试分支，做完就能逐条打勾（见[通用 01 · 先写验收标准](/blog/general-tips/01-acceptance-criteria)）；
- 约束里的第 4 条把执行节奏交给你，对应的正是 Plan 模式（见[技巧 05](/blog/workbuddy-tips/05-modes)）。

在 WorkBuddy 里操作时，再补两个动作：在输入框左下角**选择工作空间**指向项目根目录，然后用 `@` 引用上面三个文件。这样 AI 既知道「去哪找」，也知道「找什么」。

## 五、关键点与常见陷阱

**关键点**

1. 每条要素一两句话就够，四要素不是越长越好。
2. 输出一定要**可观察**——「改好 Login.tsx」比「优化登录体验」可验收得多。
3. 约束里优先写「不能做什么」，红线的价值远大于赞美。
4. 第一次派活写全四要素，后续追问可以只补其中一项（「再加上手机号登录」只补目标）。

**常见陷阱**

- **把技术选型当目标**：「用 Redux 重写状态管理」是手段，目标是「解决跨页面购物车状态不同步」。目标写成手段，AI 会照做但解决不了真问题。
- **输入堆砌无关文件**：把整个 `src/` 都引用进去，有用信息被稀释，还会挤占上下文预算（见[通用 02 · 从入口收集上下文](/blog/general-tips/02-focused-context)）。
- **约束里写模糊形容词**：「代码要优雅」「性能要好」无法执行。改成「函数不超过 40 行」「首屏接口只请求一次」。
- **忘了说输出**：不说输出，AI 默认给你一大段解释文字，而不是你要的文件改动。

## 六、动手练习与小挑战

**练习**：把下面这句话改写成四要素版本。

```text
帮我优化一下首页加载速度。
```

参考思路：

- 目标：把首页 LCP 从 4.2s 降到 2s 以内
- 输入：`src/pages/index.tsx`、Lighthouse 报告 `reports/lighthouse-home.json`
- 输出：改动清单 + 优化前后 LCP 数字对比
- 约束：不引入新的第三方依赖，不改变页面视觉与交互

**小挑战**：把改写后的版本发给 AI，观察它是否还需要反问。如果它问了问题，说明你漏掉了某一要素——找出是哪一条，补上再发一次。
