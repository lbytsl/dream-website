# 技巧 03：流程比角色更重要——别再堆砌「你是一个专家」

> 一句话概括：告诉 AI「按哪五步做」远比告诉它「你是世界顶级专家」有效——行为来自流程，不来自头衔。

{/* truncate */}

## 一、技巧名称与一句话概括

**技巧名称**：流程化提示（Process-Driven Prompting）。

**一句话概括**：把提示词里的形容词和头衔，换成有序的操作步骤、明确的判断依据和可检查的输出格式。

很多教程教你「给 AI 设定角色」，这对**文案语气类任务**有用；但在**执行类开发任务**里，角色词几乎不产生可观测的差异。真正决定产出质量的是你给的流程。

## 二、核心原理与适用场景

执行式 Agent 的行为来自三样东西：可用的工具、可读的上下文、你给的步骤。

「你是一位有十年经验的资深 React 专家」这句话，既没有增加工具，也没有增加上下文，更没有定义步骤——它主要影响回答的语气。而「先读取这个文件，列出当前校验逻辑，再用项目已有的 schema 扩展字段，最后跑一次类型检查」是实打实的行为约束。

这不是说角色完全没用。角色设定适合：

- 需要特定口吻的文档、营销文案；
- 需要模拟特定视角的评审（比如「站在安全审计者的角度」）。

但对于「改代码、跑测试、定位 Bug」这类任务，**流程 > 角色**。

**适用场景**：代码生成、重构、Bug 修复、测试编写——任何你希望结果稳定可复现的开发任务。

## 三、错误或低效写法及问题说明

```text
你是一个拥有 10 年经验的资深 React 专家，
是世界上最好的前端工程师，代码风格优雅，
请帮我给登录表单加上校验。
```

逐句看问题：

- 「10 年经验」「世界最好」：无法验证，也不改变任何决策；
- 「代码风格优雅」：无法执行的形容词，AI 只能按自己的默认风格来；
- 「加上校验」：没说校验什么、用哪种 schema、错误提示放哪、怎么验证。

结果往往是：AI 生成一段看起来很专业的代码，但用的是项目里根本没装的输入校验库，错误提示文案也和现有页面不一致。你还得自己改一遍。

## 四、正确应用方式：给登录表单加校验

假设项目里已有 `src/schemas/auth.ts`（用 zod 定义）和统一的错误提示组件。流程化写法：

```text
任务：为登录表单增加邮箱格式与密码长度校验。

执行步骤：
1. 读取 @src/pages/Login.tsx，列出当前已有的校验逻辑（如有）
2. 读取 @src/schemas/auth.ts，在现有 schema 上扩展 email 与 password 字段规则：
   - email：必填，需符合 RFC 5322 基本格式
   - password：必填，长度 8–32 位
3. 复用 @src/components/FieldError.tsx 显示错误，不要新建提示组件
4. 保持现有错误文案不变，不要改动 i18n 词条
5. 修改后运行 npx tsc --noEmit 和 npm test -- login
6. 最后用不超过 3 行说明改了什么、测试结果如何

如果第 2 步发现 schema 里已有同类规则，直接复用，不要重复定义。
```

**这段提示词为什么解决问题**：

- 第 1 步先读再改，避免 AI 覆盖你已有的校验（这是最常见的返工来源）；
- 第 2 步给出具体规则，还指定了「在现有 schema 上扩展」，防止另起炉灶；
- 第 3、4 步复用现有组件和文案，保持 UI 一致性；
- 第 5 步给了自证命令，对应[通用 01 · 先写验收标准](/blog/general-tips/01-acceptance-criteria)的验收标准；
- 最后一段是**异常分支**——AI 遇到已有规则时知道该怎么做，不会机械地重复定义。

注意，整段提示词里一个「专家」都没出现，但每一步都是可执行的。

## 五、关键点与常见陷阱

**关键点**

1. 步骤按**依赖顺序**排列：先读、再判断、后修改、最后验证。
2. 每步尽量带一个对象（文件路径、字段名、命令名），不要只写动词。
3. 为「如果发现已有实现」「如果文件不存在」这类分支留一句话，AI 就不会卡住乱猜。
4. 输出格式单独写一行（「不超过 3 行」「用表格列出」），避免长篇总结。

**常见陷阱**

- **步骤写成目标**：「优化校验逻辑」是目标不是步骤。要拆成「读取 → 识别 → 修改 → 验证」。
- **步骤之间缺依赖**：第 3 步依赖第 2 步的结果，却没说「基于上一步的 schema」——AI 可能并行处理导致冲突。
- **角色 + 流程一起堆**：既写十行角色设定又写十行流程，前面那十行纯属浪费上下文。
- **忘记写验证步骤**：AI 改完就交付，没跑过测试。第 5 步那种命令一定要写进去。

## 六、动手练习与小挑战

**练习**：把下面这段角色式提示词改写成流程式。

```text
你是一个资深的 Python 性能优化专家，请帮我优化这段代码的性能。
```

参考方向：

1. 读取 `@src/services/report.py`，定位耗时最长的函数
2. 列出每处优化点及预期收益，先给我确认
3. 只优化热点函数，不改变对外接口
4. 优化前后各运行一次 `pytest benchmarks/`，给出耗时对比

**小挑战**：同一任务分别用「角色式」和「流程式」各发一次，把两次结果交给同事盲评，看看哪一种更容易通过代码审查。
