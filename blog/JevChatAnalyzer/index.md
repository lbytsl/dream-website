## 一、先说说 Jev 是什么

2026 年 9 月 15 日，TypeSafe AI 放出了一个叫 **Jev** 的模型，开放 early access。它也在开发者圈子里刷了几天屏，但它和 GPT、Claude 那类模型**不是同一个物种**。

官方给它的定位是 **System One Model**——概念借自卡尼曼的《思考，快与慢》。它不是「系统二」那种慢思考、会推理、会写文章的模型，而是「系统一」：**一眼看过去，直接给判断**。

具体差异在接口上看得最清楚：

-   它**不生成任何文字**。不会写邮件、不会写代码、不会给你解释理由。
-   它只接受两样东西：`state`（你要判断的东西，文本 / JSON / 文本数组）和 `questions`（你希望它回答的一组问题）。
-   它**只有一个端点**：`POST https://api.typesafe.ai/v1/systemone`。注意，它**不是 OpenAI 兼容**的 `/chat/completions`。
-   它返回的是**带概率的结构化判定**，而且概率是**校准过**的。

第三种是最容易被忽略、但最重要的一点。传统小分类模型也会给你「置信度」，但那个数字不太能用——排序机制决定了它即使一个都没猜对，也会硬选一个最像的出来。Jev 的训练方法叫 **RLCD（Reinforcement Learning for Calibrated Decisions）**，目标是让置信度像靠谱的天气预报：说八成把握的时候，统计上一百次，大约真的有八十次是对的。

它一共只有三种返回原语，简单到有点朴素：

| 原语 | 干什么 | 返回什么 |
| --- | --- | --- |
| **Choice** | 从一组带标签的选项里选一个（最多 255 个） | 选中的项 + 完整概率分布 + 置信度 |
| **Score** | 把输入放到一条 2–10 级的有序谱系上 | 数值 + 分布 |
| **Noul** | 判断一个条件成不成立 | 0–1 的概率 |

速度是它最大的卖点：端到端 **70–500 毫秒**。定价也很有攻击性，输入约 **$0.042/百万 token，输出免费**（输出就是一个决策，没什么好按字收费的）。

几个需要说清楚的边界：**只支持文本**，不支持图片 / 音频 / 视频；**不支持微调**；上下文 64k；单次请求里多个问题会**并行判断、互相看不见对方的答案**，所以加问题几乎不增加延迟。

接入渠道现在有三条：TypeSafe 官方直连、**OpenRouter**（模型 ID `typesafe/jev-1.13`，9 月 18 日上架）、以及 Cloudflare / Vercel AI Gateway。国内中转站基本没有上架，因为它必须原样透传 `/v1/systemone` 这个路径——这一点我在「踩坑」一节里还会再说一次。

## 二、我为什么拿它来做「读聊天记录」

看到 Jev 的时候，我第一反应是：**这不就是聊天记录分析缺的那块吗。**

因为「读懂一段对话」这件事，本质上不是写作，是**判断**：

-   这句话是在派活，还是在求助？
-   对方现在是不满，还是只是累了？
-   我该回得热一点，还是留点空间？

这些都是**分类问题**，不是生成问题。你并不需要模型写一篇八百字的小作文来分析，你要的是一个能落地的标签、一个能用概率衡量的把握。

过去这种活儿通常两种做法：写 if-else 规则，脆得要命；或者上大模型，贵、慢、还总爱自由发挥，你得反复写提示词把它按回 JSON 里。

于是就有了这个项目：**恋爱·职场聊天神器**。一个本地运行的小工具——把一段聊天记录粘进去，选好关系场景（暧昧 / 恋爱 / 同事 / 上下级），它逐条标出每句话的**意图**和**情绪**。

项目已开源（MIT）：**https://github.com/lbytsl/jev-chat-analyzer**

标签库是人工整理、按场景过滤的：**59 个意图标签、42 个情绪标签**（情绪再分 8 个大类做二级路由）。同一个情绪在同事之间和在恋人之间叫法不一样，给同事的候选里不会冒出「小鹿乱撞」。举几个标签你感受下画风：

-   恋爱：想你了 / 约见面了 / 打情骂俏 / 患得患失 / 醋坛子翻了
-   职场：派活了 / 画饼时间 / 打太极 / 认错保命 / 压着火 / 怕出错

## 三、Jev 在这个项目里具体怎么用

这一段给想上手 Jev 的人，也是我踩了最多坑的地方。

**1）`state` 和 `questions` 的映射**

`state` 就是「这句话 + 前文 + 关系场景」三件套拼成的一个对象。`questions` 是「问题名 → 判定任务」的映射，我用的是 `choice` 类型：

```text
primary_intent  => one of: 想你了 / 约见面了 / 打情骂俏 / …
emotion_family  => one of: family_joy / family_warm / family_anger / …
```

**2）两级路由：为什么我不一次问完**

一开始我天真地把 59 个意图、42 个情绪一次性铺进候选。结果很差：**候选越多，概率越摊，平票越多**——一堆标签挤在 5%、6%、7%，你根本不知道该信哪个。

所以改成了两级：**第一次调用只判「意图 + 情绪大类」**（意图候选按场景过滤，情绪收拢到 8 个大类），**第二次再在被选中的大类里判二级标签（≤6 个候选）**。候选收窄之后，分数明显分得开了。

代价是每条消息要调两次 Jev。好在它快，长上下文下单次大约十几秒——这个「慢」不是 Jev 的锅，是整段聊天记录作为 state 的体量问题。

**3）置信度不够时，不许硬猜**

这是用 Jev 最舒服的一点：**它的概率分得开，我的阈值才有意义。**

如果二级标签的分数低于阈值，或者第一名和第二名咬得太紧，我就不展示细分标签，而是**退回到一级大类**显示——「他现在是『不爽』这一类，细分我没把握」，比硬憋一个二级标签诚实得多。

**4）两级结论打架时，以更软的那个为准**

一级判错会连坐二级。所以我加了两条修正：前两名咬得紧时，**把两个大类一起交给第二级**；如果意图判成了「调情 / 撒娇」，情绪却落在「生气 / 冷淡抽离」这种硬负面，说明两层结论互相打脸，那就**把第二级候选换成柔软的那两类**，避免输出「在调情 + 在发火」这种自相矛盾的结果。

**5）`usage` 两次都留着**

因为是两次调用，额度是按调用顺序分开记的。想对齐成本和延迟，两个都别扔。

## 四、一个必须直说的事：中文是 Jev 的短板

如果你只看宣传，可能会以为这是个全能判断器。但官方文档里有一条说得很明白：**英语是主要训练语言、准确率最好；其他语言（含中日韩）可用，但表现不均**，建议非英语负载先自测再上生产。第三方实测文章说得更直白一些：**中文场景下，它的概率校准本身会退化。**

**而我这个项目，恰好是纯中文场景。**

所以我做了几件「防身」的事，也是这个项目里我认为最值得借鉴的部分：

-   **不拿它做最终裁决。** 分类拿不准的样本会被写进本地**低置信度回流池**，供人工审阅补标签。模型不确定的地方，系统要记得住。
-   **候选永远先收窄再判**，不拿一屏标签去为难它。
-   **低置信度就降级展示**，不装作很确定。
-   **容错分层**：意图 / 情绪是 Jev 判定，属于「有概率可依」的那类；而写作类的产出（潜台词、回复建议）全部交给生成层——**因为 Jev 压根不会写字**。

最后这条其实是这个项目「双模型架构」的真正由来，不是炫技：**Jev 负责判断，另一个模型负责说话。** 生成层走的是标准 OpenAI 兼容的 `/chat/completions`，换端点只改三个环境变量（OpenAI、通义千问、智谱 GLM、Kimi、本地 Ollama 都行）。两层之间用「字段是否存在」来合并结果，跑一类不会清掉另一类。

## 五、几个真实的坑

**把 model 名字钉死。** `jev-latest` 不是模型，是**别名**——官方文档写明它解析到 `jev-1.13.0`，而**别名会随新版本发布移动**：同一批输入，答案有可能在你不改任何东西的情况下变化，你针对旧版本调好的置信度阈值会跟着失准。官方建议非常直接：**调好阈值之后，钉住版本化 ID，别用别名。**

我把项目里分类层的默认值从 `jev-latest` 改成了 `jev-1.13.0`。两个细节值得记一下：版本化 ID **不依赖 `GET /v1/models`**（那个接口目前只列别名），直接在 `model` 字段里发就会被接受；响应里的 `model` 字段会**回报实际应答的版本号**，所以每次分析的返回值我都留着它——「这条判定是哪个版本给的」应该是可查的。

**别乱拼路径。** 从 TypeSafe 原生网关切到 OpenRouter 的时候，我用同一个拼接函数无条件追加了原生路径，结果请求打到了 `/api/alpha/decisions/v1/systemone`，服务端直接 404——**看起来特别像「key 没读到」**，实际上是我路径拼错了。现在的规则是：base URL 里已经带路径就原样用，只写主机名才补 `/v1/systemone`。

**默认 UA 会被网关拒。** TypeSafe 的上游网关会拒绝 httpx / urllib 的默认请求签名，直接返回 403（error 1010）。得把 UA 伪装成浏览器。这是实测出来的，不是随手加的。

**「零幻觉」要理解成「类型安全」。** 官方说的零幻觉，意思是**输出分布只在你给定的选项内，不会编字段、编选项、编 JSON**。但**合法答案不等于正确答案**——它完全可能高置信度地选错。另外那个「置信度 0.9」是**群体口径**：说 0.9 的那一批长期约九成正确，不代表你手上这一条就有九成把握。所以阈值必须拿自己的数据调。

## 六、官方那份「毛边清单」，几乎每条都指着我的设计

写这篇的时候我翻了官方文档里最诚实的一页：**Model jaggedness**（模型的毛边），专门写给 `jev-1.13`，最后审阅日期是 2026-09-17，开头就写「这些限制是版本绑定的，其中许多会在后续版本修复」。

它列了九条失败模式。有意思的是，我回头看自己这套东西，几乎每条都能对上：

| 官方记的失败模式 | 我的对策（都在代码里） |
| --- | --- |
| **理解字面化**：答的是「你写的问题」，不是「你想问的问题」 | 每个标签都带 definition，定义还做过一轮归一化——判据跟着问题一起送进去 |
| **不是计算器**：计数与数值精度不可靠 | 一个数字都不让它算：排序、平票差值、阈值比较全在 Python 里 |
| **日期时间被当文本**：比较不可靠 | 时间只做解析（认出聊天记录里的时间行），从不把「哪个更早」交给模型 |
| **多跳推理会掉准确率** | 两级路由本质就是拆跳数：一次只判一类原子问题 |
| **state 越大越不准**：无关细节是干扰项 | 第二级只送收窄后的候选；当然，整段聊天记录当 `state` 这件事我还在观察 |
| **不保证结构性恒等式** | 全线只用 `choice`，不做跨问题的概率恒等约束 |
| **未经文本生成训练** | 潜台词与回复建议全部交给生成层——双模型架构的真正由来 |

中间那条「不保证结构性恒等式」值得单独说，因为它是反直觉的。官方举的例子是：同一句话问「要不要退款」（`noul`）得到 0.72，问它的否定形式得到 0.47——**加起来 1.19**。也就是说，两个互补问题并不互斥，你不能拿算术恒等式去约束它。

还有一条提醒正好戳在我这个项目的软肋上：**不要把一个在 `noul` 上调好的阈值迁移到 `choice`**。因为 Choice 是**相对判断**（在选项里挑一个），Noul 是**绝对判断**（可以全部都很低）。我全线都用 Choice，所以阈值是 `choice_probability` 口径——代码里连这个口径都显式记着（`score_kind: 'choice_probability'`），免得半年后自己搞混。

最后回到那条「非英语负载先自测」：这就是为什么**低置信度回流池不是锦上添花，而是必需品**。

## 七、如果你也想上手

**Jev 侧**，两条路二选一：

-   官方直连：`TYPESAFE_BASE_URL=https://api.typesafe.ai`，代码里补 `/v1/systemone`
-   OpenRouter：`TYPESAFE_BASE_URL=https://openrouter.ai/api/alpha/decisions`，模型名 `typesafe/jev-1.13`

**项目侧**，后端用 uv、前端用 pnpm：

```bash
git clone https://github.com/lbytsl/jev-chat-analyzer.git && cd jev-chat-analyzer

uv sync --no-dev          # 后端依赖，自动建 .venv
cp .env.example .env      # 填 Jev（分类层）+ 生成层两套配置
cd frontend && pnpm install
```

macOS 双击 `启动.command`，Windows 双击 `start.bat`，会自动起后端（8767）和前端 dev server（5173）并打开页面。顶栏「配置」里分别填分类层与生成层，底部「测试连接」可以先验证再保存——保存后**下一次请求就用新配置，不用重启**。接口文档在 `http://127.0.0.1:8767/docs`。

**隐私**：工具在本地运行，会话保存在本机 `var/sessions.db`。调用你配置的远程模型 API 时，对话文本仍会发送到对应服务；本地运行不等于数据始终不离开本机。删除本地会话文件也不等于删除远程服务可能保留的记录。

## 八、关于 Jev 的一点冷静话

写到这里得泼点水，否则这篇文章就不值钱了。

Jev 不是「更聪明的模型」，它是「**更适合被软件调用的判断**」。这意味着：

-   官方自设评测里，Jev 工作流准确率约 **67.8%**，前沿模型区间是 **68%–74%**——**水平接近，而非超越**。「快 193 倍、便宜 444 倍」也是自家设定的工作流口径，官方自己承认那偏向收益上限。
-   独立测试里有更冷的数字：有人拿德州扑克 GTO 求解器当标准答案，150 个决策点吻合率 63%，到了真正有争议的 55 个点位只剩 38%。
-   也有人质疑它「不就是一个分类器」、认为约束解码加受限 logit 切片现在就能复现类似形状。TypeSafe 创始人 Diogo Almeida 在 Hacker News 上的回应是：约束解码会让模型变笨，会给非法 token 分配概率的模型本身就是糊涂的。

我的结论比较朴素：**它确实是个分类器，但分类的标签可以在运行时定义**——今天问三个部门，明天从两百个选项里挑一个。这就是它和训练时标签固定死的传统分类器的区别，也是它值得被放进流水线的理由。

所以正确定位不是替代大模型，而是分工——

> Code 管「文件存在吗、HTTP 200 吗」，\
> **Jev 管「这是哪类任务、风险哪一档、重试还是降级」**，\
> LLM 管「怎么拆任务、怎么写代码」，\
> Human 管「删文件、发邮件、花钱」。

按这个分工，聊天记录分析恰好落在 Jev 那一格：**海量、细小、不值得叫醒推理模型的判断**。而潜台词和回复建议，老老实实交给会写字的模型。

这就是我用 Jev 做的这个东西的全部理由。
