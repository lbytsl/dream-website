同一个仓库里反复提醒 AI「不要改生成文件」「改搜索后跑这组测试」，就该把这些稳定约定写下来。

## 技巧名称与一句话概括

仓库级约定：让项目规则成为可版本管理、可执行的短文档。

## 核心原理与适用场景

长期约定解决每个开发任务都要重复说的问题；任务提示词解决当前要交付什么。自动读取的文件名、作用域和优先级因工具和版本而异，文档本身也不是权限保护。

## 低效写法与问题

> 所有代码都要优雅，改完一定要测。把历史决策、所有接口和测试账号也写进去。

「优雅」无法检查，「要测」没说怎么测。冗长背景会掩盖真正的边界；测试账号和访问凭据不应进仓库。

## 正确应用与代码解释

```md
# 搜索模块约定
- 改标题搜索时运行 `npm run test:search`，报告命令与结果。
- 不直接编辑 `src/generated/`，修改生成源再生成。
- 需要改公共 API 时先列出调用方，未经确认保持旧字段可读。
```

示例中命令应替换成仓库里确实存在的脚本。每条规则都说明什么时候适用以及如何验证；团队可以随代码一起审查它，而不用每次重写提示词。

## 关键点与常见陷阱

- 写明规则适用的目录和例外；过期命令会误导下一轮开发。
- 不把流程模板、API 全量文档堆进入口文件，给更详细的文档留链接。

## 动手练习与小挑战

练习：挑一个你反复提到的约定，写成「条件 → 动作 → 验证」三段。挑战：用自己所用工具在新会话做一次只读检查，确认它实际看到哪份规则。
